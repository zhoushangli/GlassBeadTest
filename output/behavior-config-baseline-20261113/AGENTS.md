## 项目环境

1. 当前项目是 Godot 4.7 系列的 2D 羊、狼与牧羊犬模拟，业务代码使用 GDScript，行为树使用 LimboAI GDExtension。
2. 主场景为 `Levels/Map/SCN_Root.tscn`。`g_gameplayEngine` 是唯一的 GameplayEngine Autoload，由 `Prefabs/Runtime/Core/SCN_GameplayEngine.tscn` 创建。
3. 使用与项目及 LimboAI 扩展兼容的 Godot 可执行文件。涉及 Godot 行为或兼容性时，可读取源码 `C:\Work\Godot\Editor\godot`，并核对源码与运行版本是否一致。
4. 运行或构建前先检查 `.vscode/tasks.json`，存在时优先参考已有任务；当前项目尚未提供该文件，不假定存在 C++、C# 构建流程。

## 当前代码职责

1. `Scripts/Core/GameplayEngine.gd`：统一模拟步进、随机数、暂停与重置、草的消耗和恢复。
2. `Scripts/Core/EntityService.gd`：实体创建与移除、空间索引、羊群统计与捕获结算。
3. `Scripts/AnimalController.gd`：单只动物的状态、感知事实、行为动作、移动和交互。
4. `Resources/AI/BT_*.tres`：各动物的行为优先级和分支组合。`Scripts/AI/Tasks/` 提供条件读取与动作调用，新增行为优先沿用这条链路。
5. `Scripts/RootController.gd`：场景启动、场地与草的表现。`Scripts/Core/DebugService.gd` 和 `Scripts/UI/DebugHUD.gd`：调试输入、选择与状态显示。
6. `Scripts/Core/SimulationConfig.gd` 和 `Resources/Gameplay/CFG_Simulation.tres`：共享模拟参数。动物专属速度、颜色和行为树引用放在 `Prefabs/Runtime/Objects/` 对应场景中。
7. 以上是当前实现的职责划分；讨论中的设计目标与已经实现的行为应分开表述，不将提议写成既有功能。

## 文件修改规则

1. 不要回滚用户已有修改，除非用户明确要求。
2. 修改范围应尽量小，只改和任务直接相关的代码、场景或资源。
3. 非必要不要新增类；优先修改已有函数和已有数据结构，除非现有职责明显不适合。
4. 不要为了通用性提前设计复杂接口或额外框架，先满足当前项目需求。
5. 优先遵循项目已有命名、目录和调用方式，保留 `Scripts`、`Resources`、`Prefabs`、`Levels`、`Art`、`Tests` 的分工。
6. 不顺带修改 `addons/` 第三方插件；`.godot/` 是生成缓存，`output/` 是临时验证、截图和历史对照资料，不把其中的副本当成当前源码。
7. 修改场景与资源时保留无关属性和已有引用，不为整理格式重新生成整个文件。

## GDScript 代码风格

1. 使用项目现有的 Tab 缩进；函数和变量使用 `snake_case`，类型使用 `PascalCase`，常量与枚举值使用 `UPPER_SNAKE_CASE`。
2. `if`、`elif`、`else`、`for`、`while` 和 `match` 的语句体使用独立的缩进行，不写单行控制语句。GDScript 不使用 C++ 风格的花括号。
3. 相邻的小逻辑段之间空一行，同一逻辑段内紧密相关的语句保持连续；函数之间沿用已有的空行风格。
4. 同一枚举或按键的多分支分发优先使用 `match`，相同处理逻辑共用分支；有效性检查、状态条件和提前返回保留 `if`，不强行改写简单判断。
5. 自定义类型和常量放在字段、函数之前；导出配置、节点引用、运行时字段分别成组，函数按职责分组。保持字段初始化依赖，不为排版改变行为。
6. 能明确类型时沿用已有类型标注或 `:=` 推断；需要与 Godot、LimboAI 动态接口配合时，不为了类型形式引入额外包装。
7. 模拟时间与随机行为沿用统一步进和 `gameplay_engine.rng`，保留暂停、单步和固定种子重现能力；不在表现代码中另起一套模拟更新。

## 注释规范

保留流程编号和效果说明两类约定，GDScript 使用 `#`。

### 流程类注释

用于说明执行步骤：

```gdscript
# 1) Initialize state
# 2) Check conditions
# 3) Apply results
```

### 效果类注释

用于说明函数、变量或行为的实际效果，使用两行，第二行给出例子：

```gdscript
# Return the nearest grass index that still has food, or -1 if none remains.
# e.g. find_grass(Vector2(340.0, 240.0))
```

注释语言沿用所在文件；不为简单、直接的代码堆砌注释。

## 运行与验证

1. 修改 GDScript、场景或资源后，执行相关解析、导入或最小运行验证；普通项目修改无需重新编译 Godot 引擎。仅修改文档、注释时无需运行模拟。
2. 优先使用已有局部验证入口。`Tests/SimulationVerification.gd` 是现有整体行为验证脚本，`Tests/RunBenchmark.gd` 是性能采样脚本；可通过 Godot 的 `--path <项目目录> --script res://Tests/<脚本名>.gd` 运行，无窗口行为验证可加 `--headless`。
3. 缺少独立入口时，采用可行的最小验证并说明覆盖限制，不自动执行整套验证或顺带重构验证体系。完整回归用于阶段收尾、用户明确要求，或实际影响范围需要的情况。
4. 同一版本验证通过后，仅在新增修改、出现失败或存在具体未解决问题时重复或扩大验证；复用当前兼容的 Godot 和已导入资源。
5. 修改统一步进、空间查询、实体生命周期或行为优先级等公共机制时，按实际影响覆盖相关动物和交互。新增检查优先覆盖修复过的 bug、重要边界和跨模块连接。
6. 各验证模块自行准备最小测试数据，避免依赖其他测试的执行结果；断言检查行为契约，减少对子节点顺序等内部细节的依赖。低风险、可逆修改不为凑覆盖新增测试。
7. 行为调试优先固定随机种子并使用暂停、单步、选中实体和状态显示。群体是否自然流动、颜色形状是否易辨认等效果需要实际运行观察，不能仅凭解析或断言通过判定。
8. 性能结论应说明实体数量、模拟时长、渲染模式、帧率上限及运行方式；无窗口模拟耗时与桌面渲染帧率分别表述。
9. 交互预览应可直接打开；截图、视频和证据导出按视觉调试或交付需要执行，放在 `output/` 对应目录，避免覆盖已有证据。
10. 完成后用一至两句说明验证范围、结果和必要的覆盖限制。解析/导入、自动行为验证与桌面交互验证分别表述；无法执行必要验证时说明原因。

## Agent 工作方式

1. 开始任务前先阅读相关代码，不要直接猜实现。
2. 如果没有明确说明执行修改，先讨论需求和矛盾处，明确后再修改；用户已经明确要求或确认的修改直接执行，不重复询问同一授权。
3. 同一请求中，区分明确要求执行的修改与尚在讨论的设计。涉及群体行为、饥饿、碰撞等机制时，先说明当前规则、预期效果和取舍，不把讨论选项自动当成完整实施方案。
4. 保留用户关于小范围修改、简洁代码、成员分组、注释和逐步讲解的长期偏好；针对当前技术栈调整表达，不因旧规则来自其他项目就一并删除这些偏好。
5. 完成后简要说明修改文件、行为变化和验证结论；仅在失败或存在具体风险时展开，不逐项复述检查过程。

## 代码讲解方式

1. 由浅入深，先讲清基础思想和职责。用直白的语言说明谁储存数据、谁负责表现、谁维护逻辑，以及它们如何配合。
2. 从最简单的具体例子开始，逐步引入特殊情况。每次说明新情况为什么让原有做法不够用、会影响哪些流程，以及需要做什么改动。
3. 按照“例子 → 新问题 → 影响 → 改动”的顺序循环推进。根据理解程度逐步加深，最后串起完整流程，落实到当前项目，带着用户完成所需功能。
